# 自动结算

为减少小团队管理员的操作，普通请求异常不再长期保留预占。模型调用是否成功与本地额度是否结算分别处理：流中断仍向客户端报错，不伪造正常结束；已经收到的可靠用量则自动入账。

| 情况 | 本地额度处理 |
| --- | --- |
| 正常完成且有可靠用量 | 按原价格快照结算，释放预占差额 |
| 断流、取消、未完成响应但已取得可靠用量 | 按已记录用量自动结算，释放预占，在日志说明异常 |
| 缺失/不完整/无效用量 | 按 0 结算并释放预占，日志明确说明 |
| 请求未发给上游或上游明确拒绝 | 按 0 结算，不保留预占 |
| 服务重启时仍有在途/旧待核算记录 | 有可靠持久化用量则按原快照结算，否则按 0 释放预占 |
| 账本写入失败、快照损坏等结算异常 | 保留待核算及预占，管理员检查；下次启动尝试恢复 |

可靠用量要求明确的非负输入/输出统计，缓存和思考用量按原适配规则处理。负值、缓存超过总输入等无效统计不会拿前一个看似有效样本来扣款；仅有输入而缺少输出也不会假设输出为 0。用量逐步到达时，Responses 总输入与缓存分别合并，再计算未缓存输入，避免重复计费。

按 0 处理是团队内部不分摊这笔不确定消耗的策略，不代表上游实际免费；中断时已收到的用量也可能少于上游最终计量。不会自动重放模型调用。

## 持久化与恢复

结束请求时先保存用量与失败原因，再在同一事务内提交额度扣除、预占释放和日志金额。若事务失败，保留证据、未释放预占与待核算标记；待核算日志不受普通日志过期清理影响。结算幂等，不重复扣款，人工核算和已结算记录不会被自动覆盖。仍按请求原来绑定的 5 小时/7 天窗口结算，不扣到管理员重置后的新窗口。

启动恢复在单实例文件锁下、接受新请求前执行，也会处理历史版本留下的待核算记录。恢复功能不得在运行中对当前在途请求执行。没有新的数据库迁移，schema 仍为 6。

## 升级与查看

备份原数据库和主密钥，按 [部署文档](deployment.md) 切换 程序并重启。旧待核算记录会在首次启动按上述策略自动处理；已经结算的历史账单不变。网页请求日志展示金额与原因，结算异常合并到管理员请求日志，可筛选异常并查看详情、重试或人工核算，不再提供独立页面。

新流程使用模拟上游和临时数据库验证：断流、取消、JSON/SSE 未完成用量、缓存延后到达、无效 usage、原价格快照、重复恢复、数据库失败回滚、日志持久化失败及待核算证据保留。不使用真实上游进行新增计费测试。

验证命令：`go test -race ./...`、针对最终结算状态调整的 store/gateway/recovery 竞态回归、`go vet ./...`、前端单元测试和发布二进制 6 项浏览器测试均通过；新旧变量两套本地 Docker 初始化、登录及重启持久化检查通过，临时资源已清理。当前运行进程未被自动重启，也没有直接更改其既有待核算记录。
